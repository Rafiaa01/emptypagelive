FASTAPI · SUPABASE · POSTGRES

Auth API

A production-shaped authentication API — signup, login, session handling, and rate limiting — built on FastAPI with Supabase as the identity and data layer.

View repo Ask about this build

The problem

Most tutorial auth flows work until real traffic hits them. This project was about building an auth API that behaves correctly under the conditions that actually break auth: repeated login attempts, expired sessions, and concurrent signups — not just the happy path of one user signing up once.

How it's built

FastAPI handles routing and request validation, with Supabase providing managed Postgres, user identity, and row-level security. The API exposes endpoints for signup, login, token refresh, and session invalidation, with request validation enforced at the schema level before anything touches the database.

What I'd explain if you asked

  • Why FastAPI over Flask here: built-in request validation via Pydantic models cuts down a whole category of malformed-input bugs before they reach business logic.
  • How Supabase's row-level security policies are used to keep one user's data from being reachable by another user's session token.
  • Where rate limiting sits in the request lifecycle, and why it's applied before the database call rather than after.
Honest accounting

What broke: initial rate-limiting logic let repeated failed logins through without a backoff window, which meant a scripted attempt could hammer the login endpoint. That was found and fixed during testing, not caught by design — a reminder that rate limits need to be tested adversarially, not just implemented and assumed to work.

What's still rough: no automated test suite yet — testing so far has been manual, via requests against a local instance.
